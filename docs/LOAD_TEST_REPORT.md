# Clever Monkey — 부하·스트레스 테스트 리포트

**일자**: 2026-06-11
**대상 커밋**: `main` (다중 프로바이더 라우팅 적용 후)
**방식**: 인프로세스 핸들러 부하 + 라우터 장애주입 + 로컬 성능 벤치 + 공개 무료 한도 기반 용량 산정

---

## 0. 요약 (TL;DR)

| 항목 | 결과 |
|---|---|
| **치명 결함 발견·수정** | IP 레이트리미터 O(n²) → 단일 IP 폭주 시 함수 CPU 마비 (DoS). 수정 후 **6,000배** 개선 |
| **인프라 한계** | 1 웜 인스턴스가 검증 경로 기준 **~200,000 req/s** 처리, 1,000 동시요청 3ms |
| **진짜 병목** | 우리 코드가 아니라 **Gemini 무료 티어 일일 한도(RPD)**. 여기가 천장 |
| **천장을 올린 것** | 작업별 라우팅 + Groq/Cerebras 폴백으로 유효 일일 한도 **약 250 → 15,000+ 요청/일**로 확장 |
| **실제 동시 사용자 추정** | 무료 티어 조합으로 **일 700~1,500 활성 사용자**까지 품질 저하 없이 수용 가능 |

> ⚠️ **측정 한계**: 이 에이전트 실행환경의 네트워크 정책이 `clever-monkey.netlify.app` 아웃바운드를 차단(`Host not in allowlist`)하여 **프로덕션 실서버에 직접 부하를 가하지는 못했습니다.** 대신 배포된 것과 **동일한 핸들러/라우터/유틸 코드를 인프로세스로 실행**해 측정했고, 외부 AI 호출은 무료 한도 소진을 피하려 의도적으로 호출하지 않았습니다(검증 단계에서 차단되는 요청 형태 사용).

## 1. 테스트 계획

| # | 카테고리 | 무엇을 | 방법 |
|---|---|---|---|
| 1 | **레이트리밋/새로고침 폭주** | 한 IP가 새로고침으로 함수를 연타 | `tooManyRequestsByIp`에 100만 호출 |
| 2 | **메모리/규모** | 수십만 고유 IP 추적 시 메모리 | 50만 고유 IP 주입 |
| 3 | **핸들러 처리량** | 검증 경로 순차/동시 처리량 | 5,000 순차 + 1,000 동시 |
| 4 | **페이로드/용량** | 4MB 바디·25만자 프롬프트 상한 | 초과 페이로드 주입 |
| 5 | **모델 과부하/폴백** | 프로바이더가 429/503/504 쏟을 때 | Gemini 50~100% 실패 주입 후 1,000 동시 |
| 6 | **키풀 회전** | 멀티키 라운드로빈 공정성/속도 | 100만 pick + 전체 소진→쿨다운 |
| 7 | **대용량 문서** | 10MB 문서 토큰추정/샘플링 | 10MB 입력 |

원칙: **무료 AI 한도를 테스트로 소진하지 않는다.** 실제 모델 호출은 수행하지 않고, 장애는 모킹으로 주입.

## 2. 발견 사항

### 🔴 결함 #1 — IP 레이트리미터 2차 복잡도 (수정 완료)

**증상**: 한 IP가 1분 창 안에서 한도를 넘겨 계속 호출하면, 코드가 한도 초과 여부와 무관하게 매 호출마다 타임스탬프를 배열에 push했고, 매 호출이 전체 배열을 `filter`로 훑었습니다. 배열이 무한히 커지며 호출당 비용이 O(n) → 전체 O(n²).

**실측 (수정 전)**: 단일 IP 200,000 호출에 **224,470ms (891 ops/s)** — 한 IP의 새로고침 폭주만으로 함수 CPU를 마비시키는 **DoS 벡터**.

**수정**: 창이 가득 차면 타임스탬프를 기록하지 않고 거부. 배열을 `RATE_LIMIT_MAX(30)`개로 상한 → 호출당 O(30) 상수.

**실측 (수정 후)**: 1,000,000 호출에 **187ms (5,352,755 ops/s)** — 약 **6,000배** 개선. 회귀 방지 테스트로 고정(`tests/stress/infra.stress.test.ts`).

### 🟢 개선 #2 — 레이트리밋 맵의 유휴 IP 정리

고유 IP당 약 **281 bytes**, 50만 IP에서 힙 **+134MB**가 관찰되었습니다. Netlify 함수는 콜드스타트마다 초기화되므로 즉시 위험은 낮지만, 장수 웜 인스턴스에서는 유휴 IP entry가 남을 수 있었습니다.

**2026-06-18 후속 조치**: `tooManyRequestsByIp`가 기존 분당 30회 차단 기준과 O(30) 단일 IP 상한은 유지하되, 60초 rate window가 지난 유휴 IP entry를 주기적으로 prune하도록 변경했습니다. 반복 burst 중 매번 전체 Map을 훑지 않도록 prune 간격은 rate window와 같게 두었습니다.

### 🟢 양호 — 핸들러 처리량

- 순차 검증 경로: **~203,000 req/s** (1 웜 인스턴스)
- 1,000 동시요청: **3ms**, 전부 정상 400 반환
- 4MB 초과 바디 → 413, 25만자 초과 프롬프트 → 400 (프로바이더 호출 전 차단 확인)
- 잘못된 JSON 200건 동시 → 전부 400

검증·차단 경로는 우리 인프라의 병목이 전혀 아님.

### 🟢 양호 — 모델 과부하 시 폴백 (핵심)

라우터에 장애를 주입한 결과:

| 시나리오 | 결과 |
|---|---|
| Gemini **50% 실패** + 1,000 동시 (퀴즈, JSON) | **사용자 노출 에러 0건** — 전부 유효 JSON 반환, 일부 Groq로 폴백 |
| Gemini **100% 다운** + 300 요청 (요약) | 전부 Groq/Cerebras가 처리 |
| Gemini가 JSON 작업에 산문 응답 | 자동으로 다음 프로바이더로 폴백해 유효 JSON 확보 |
| **전 프로바이더 동시 다운** | 그제서야 에러 (예상된 동작) |
| Gemini 70% 프리스트림 실패 + 500 동시 스트림 (팟캐스트) | 500개 스트림 전부 완결 |

→ 사용자가 겪던 **팟캐스트 504**는 이제 라우팅 계층에서 흡수됨.

### 🟢 양호 — 키풀

- 100만 pick **65ms (15.4M ops/s)**, 3키 분포 **333334/333333/333333** (완벽 균등)
- 전 키 소진 시 `pick()`이 null 반환, 쿨다운(50ms) 후 자가복구 확인

### 🟢 양호 — 대용량 문서 유틸

- `estimateTokens` 10MB: **552ms** (실제 상한 25만자≈0.25MB 기준 환산 ~14ms)
- `sampleEvenly` 10MB→12만자: **0.3ms** (사실상 즉시)

## 3. 용량 산정 (실제 천장 = AI 일일 한도)

우리 인프라는 초당 수만 요청을 견딥니다. **실질 천장은 외부 무료 AI 한도**입니다.

### 작업당 AI 호출 수 (라우팅 적용 후)
- 문서 처리: 요약(스트리밍) + 추천질문 = **2회** (텍스트 PDF는 추출 0회 — 클라이언트 pdf.js)
- 퀴즈/플래시카드/마인드맵/슬라이드/팟캐스트: 각 **1회**
- 채팅: 메시지당 **1회** (countTokens 제거됨)

### 무료 일일 한도 (공개 기준, 프로젝트 단위)
| 프로바이더·모델 | 대략 RPD | 라우팅상 역할 |
|---|---|---|
| Gemini 2.5 Flash-Lite | ~1,000/일 | 다수 작업 1순위 |
| Gemini 2.5 Flash | ~250/일 | 품질 폴백 |
| Groq 8B instant | ~14,400/일 | 경량·대량 1순위 + 폴백 |
| Groq 70B / Qwen 32B | ~1,000/일 | 폴백 |
| Cerebras | ~1,000/일 | 예비 |

→ 단일 Gemini 의존(약 250~1,000/일)에서 **합산 유효 ~15,000+ 요청/일**로 확장.

### 활성 사용자 환산 (보수적, 사용자당 하루 ~10 AI 작업 가정)
- **이전(Gemini만)**: ~25~100 활성 사용자/일에서 한도 소진
- **현재(라우팅+폴백)**: **약 700~1,500 활성 사용자/일** 품질 저하 없이 수용 가능
- 무료 티어 일일 제한(`increment_ai_action`, Free 20회/일)이 폭주 사용자를 자동 차단 → 한 사람이 한도를 독식하지 못함

> 참고: 이 환산은 `SUPABASE_SERVICE_ROLE_KEY`가 Netlify에 설정돼 사용량 미터링이 동작할 때 유효합니다.

## 4. 동시성·버스트 한계

- **새로고침 연타 1인**: 분당 30회 초과분은 즉시 429 (이제 O(30) 상수 비용). 정상 사용자에게는 충분, 어뷰저는 저비용 차단.
- **동시 업로드**: 인프라상 1,000 동시 검증 3ms. 실제 병목은 동시 업로드들이 만들어내는 AI 호출 수 → RPM(분당) 한도(Flash-Lite ~15 RPM, Groq ~30 RPM)가 먼저 닿음. 닿으면 폴백 체인이 다른 프로바이더로 분산.
- **Netlify 함수 동시성**: 무료 플랜 기본 동시 실행 한도가 별도 천장(보통 수십~수백). 트래픽 급증 시 이 부분이 큐잉될 수 있으나, 스트리밍 전환으로 함수 점유시간 자체가 줄어 회전율 개선.

## 5. 권장 후속 조치 (우선순위순)

1. **(완료)** 레이트리미터 2차 복잡도 수정 — 배포 필요
2. **(선택)** Groq/Cerebras 키를 Netlify에 설정 → 폴백 실제 활성화 *(사용자가 이미 추가 완료)*
3. **(완료)** 레이트리밋 맵 유휴 IP 주기적 정리 — 장수 웜 인스턴스 메모리 안정화
4. **(선택)** 분당(RPM) 한도가 잦게 닿으면 작업 큐/지수백오프 도입 검토
5. **(권장)** `SUPABASE_SERVICE_ROLE_KEY` 확인 — 미터링·일일 제한의 전제

## 6. 재현 방법

```bash
npm run test:stress     # 인프라+라우터 부하 스위트 (tests/stress/)
npx tsx --expose-gc /tmp/bench.mjs   # 독립 성능 벤치 (수치 출력)
```

스트레스 스위트는 기본 `npm test`에서 분리되어 있습니다(전역 키풀 상태 변경·대용량 루프 때문). 실제 AI 호출은 하지 않으며 무료 한도를 소비하지 않습니다.
